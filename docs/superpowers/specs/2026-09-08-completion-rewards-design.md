# 通关奖励系统设计

## 目标

在现有“深度调查”循环上增加长期收藏反馈：玩家完成案件后获得纪念藏品，满足高分、全线索或无提示条件时获得专精徽章与 ARCHIVE/OS 预置主题。奖励用于展示和外观，不提供提示点、答案或数值优势。

## 玩家体验

1. 提交推理后，结算页显示本次获得的全部奖励，并突出首次解锁项目。
2. 档案馆导航增加“馆藏奖励”，集中展示已知奖励、锁定条件和来源案件。
3. 已解锁主题可以在馆藏奖励中装备；主题立即应用到档案馆、案件桌面、应用窗口和结算页。
4. 重开案件不会清除奖励。重复通关不会重复创建记录，但可以继续刷新最高分和案件专精。
5. 未安装案件留下的已解锁奖励继续保留，并显示原始案件标题快照。

## 奖励类型

- `artifact`：完成案件即可获得的故事纪念藏品。
- `badge`：满足全线索、高分、无提示等复玩条件后获得的专精徽章。
- `theme`：满足较高要求后解锁的视觉主题。主题仅能引用主应用内置白名单，不允许案件提供 CSS 或远程资源。

档案 001 提供“未启程登机牌”、无提示徽章和“候机厅夜色”主题；档案 002 提供“停播节目单”、完整记录徽章和“信号室蓝图”主题。缺少自定义奖励的旧案件自动获得一个通用结案藏品和一个完整归档徽章。

## 数据模型

`InvestigationGameplayDefinition` 增加可选的 `rewards` 数组。每项奖励包含案件内 ID、类型、标题、说明、解锁条件，以及主题奖励可选的白名单 `themeId`。现有 `GameplayRequirement` 继续作为唯一条件语言；奖励只在存在推理结果时结算，空条件表示完成一次推理即可获得。

跨案件奖励写入独立的本地 `RewardProfile`：

- `version: 1`
- `unlocks`: 以 `<caseId>:<rewardId>` 为唯一键的解锁记录，保存奖励标题、类型、来源案件标题和首次解锁时间快照
- `selectedTheme`: 当前装备的白名单主题

奖励定义可以随案件发布，但解锁状态不写入案件 Definition；系统不信任案件自报的“已解锁”状态，也不随案件卸载自动删除奖励记录。玩家存档继续记录本次结算的奖励 ID，便于结算页准确区分“本次获得”和“首次解锁”。

## 组件与边界

- `gameplay/rewardEngine.ts`：纯函数解析默认奖励、判断条件、生成本次奖励。
- `rewards/rewardProfile.ts`：容错读取、去重写入和主题白名单校验。
- `rewards/rewardStore.ts`：向 React 和 `gameStore` 提供解锁与装备操作。
- `rewards/archiveThemes.ts`：唯一允许的主题 ID、显示名称和 DOM 应用函数。
- `features/rewards/RewardCollection.tsx`：档案馆内的奖励目录和装备界面。
- `ResultScreen`：显示本次奖励与首次解锁标记。
- `OutcomeEditor`：作者可以增加、编辑和删除奖励，但主题只能选择白名单 ID。

## 兼容性与安全

- 案件格式版本仍为 1；`rewards` 为可选字段。
- 旧案件、旧 `.ldmcase` 和旧编辑器工程通过确定性默认奖励继续运行。
- 推理结果中的奖励字段为可选字段，旧存档不需要迁移版本。
- 奖励资料按普通不可信文本由 React 渲染，不使用 HTML 注入。
- 案件不能定义颜色、图片 URL、CSS、脚本或任意主题标识。
- 损坏的奖励资料返回空收藏和默认主题，不影响案件启动。

## 可访问性与视觉

馆藏奖励采用紧凑档案目录，而不是商城卡片。每项奖励同时显示文字状态和类型，不只依赖颜色；主题按钮有明确的“装备”“当前使用”和禁用状态；结算页新增区域使用 `aria-labelledby`，首次解锁使用可读文字标记。主题保持现有高对比度与 reduced-motion 行为，不增加闪烁或持续动画。

## 测试与验收

- 奖励引擎：仅在完成推理后解锁、条件判断、默认奖励、重复结算去重。
- 本地资料：损坏数据恢复、非法主题回退、跨案件奖励并存、重开案件保留。
- 组件：结算页首次奖励、馆藏奖励锁定/解锁、装备主题、案件卡奖励数量。
- 编辑器：新增奖励、切换类型、主题白名单、校验错误。
- 回归：旧案件无 `rewards` 仍可导入、两案完整流程、社区校验、生产构建和 Playwright。

验收标准：每个内置案件至少一个通关藏品和一个进阶奖励；奖励首次解锁反馈清晰；重复通关不重复计数；主题可以装备并刷新恢复；重开、卸载或社区离线不会破坏已获得奖励。
